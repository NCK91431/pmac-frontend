## 1. 概述

### 1.1 项目背景

在现有「日前用电需求申报工作流」（v1）之外，独立构建 **v2 版本** 的全新页面。v2 版本采用 **三步流程** 设计，显著增强了数据看板、AI 辅助查询、多日期电价横向对比等功能，并升级了策略申报表为 16 列双表头结构。

### 1.2 关键约束

| 约束项 | 说明 |
|--------|------|
| **页面关系** | 全新的独立页面，**不修改** v1 的 `DailyDemandReport.vue` |
| **组件复用** | 可复用 `AuxiliaryTradingTools/components/` 下的通用子组件 |
| **路由独立** | 新增独立路由路径，不与 v1 共享路由 |
| **UI 框架** | Element Plus + Bootstrap 5（维持项目现有技术栈） |
| **请求库** | `@/utils/request.js`（axios 封装实例） |
| **图表库** | ECharts 5 |
| **状态管理** | Pinia（按需引入，如果状态简单则页面内维护） |
| **设计稿** | [`新需求文档/日前用电侧申报V2设计稿.html`](/Users/guansiyu/Desktop/frontend-code/新需求文档/日前用电侧申报V2设计稿.html) |
| **样式标准** | 所有新建组件的样式须 **100% 严格遵循设计稿**；复用组件（来自 `AuxiliaryTradingTools/components/`）保持原始样式，不做任何修改 |

## 2. 路由设计

### 2.1 路由路径

建议采用 `/daily-demand-report-v2` 作为基础路径，与 v1 的 `/daily-demand-report` 区分。

| 路由 | 名称 | 组件 | 说明 |
|------|------|------|------|
| `/daily-demand-report-v2` | `DailyDemandReportV2` | `DailyDemandReportV2/index.vue` | 主页面（三步流程容器） |
| `/daily-demand-report-v2/history` | `DailyDemandReportV2History` | `DailyDemandReportV2History.vue` | v2 历史记录查看页 |

> **说明：** v2 的历史接口与 v1 不同（`/api/daily-declaration/v2/history/dates`），因此历史页也需要独立。

### 2.2 路由注册

在 `src/router/index.js` 中新增路由配置：

```javascript
{
    path: '/daily-demand-report-v2',
    name: 'DailyDemandReportV2',
    component: () => import('@/AuxiliaryTradingTools/DailyDemandReportV2/index.vue'),
    meta: { permission: 'internal' }
},
{
    path: '/daily-demand-report-v2/history',
    name: 'DailyDemandReportV2History',
    component: () => import('@/AuxiliaryTradingTools/DailyDemandReportV2/History.vue'),
    meta: { permission: 'internal' }
},
```

### 2.3 侧边栏菜单

在 `sidebarMenuConfig.trading.children` 中新增菜单项：

```javascript
children: [
    { title: "日前交易申报", route: "/daily-demand-report" },       // v1（保留）
    { title: "日前交易申报v2", route: "/daily-demand-report-v2" },  // v2（新增）
    { title: "历史申报", route: "/daily-demand-report/history" },    // v1 历史（保留）
    { title: "月度需求申报", route: "/monthly-demand-report" },
]
```

### 2.4 面包屑映射

在 `Breadcrumb.vue` 的 `routeToBreadcrumb` 中新增：

```javascript
DailyDemandReportV2: {
    title: "日前交易申报v2",

    icon: "bi bi-clock-history",
```

## 4. 数据流与状态管理

### 4.1 核心数据流

```
Step 1（选择申报日期）
    │
    │   declaration_date, dateInfo（日期信息 + 天气/温度）
    │
    ▼
Step 2（筛选可用数据源）
    │
    │   selectedDates（选中的历史日期列表）
    │
    ▼（点击「下一步」，链式调用两个接口）
① price-comparison-table API → priceSpreadInfo（价差方向 + 日前低概率，24时段）
    │
    ▼（成功后直接整理响应数据，调用 strategy-data）
② strategy-data API → strategyData（16列数据）
    │
    ▼
Step 3（申报 — 策略申报表）
    │
    │   adjustedRatios（用户调整后的比例）
    │   actualDeclaredQuantities（用户调整后的电量）
    │
    ▼
    Submit（提交申报）
```

### 4.2 状态管理策略

使用 **Pinia store**（`useDailyDeclarationV2Store`）管理全局状态，原因：
- 三步流程之间需要共享大量数据
- 步骤间的数据传递复杂（Step 2 → Step 3 需要传递 24 时段的价差方向/概率）
- 历史记录查看时需要回填所有步骤数据

**Store 结构：**

```javascript
// stores/dailyDeclarationV2.js
{
    // Step 1 数据
    declarationDate: '',              // 目标申报日期
    dateInfo: null,                    // 日期详情（manual-date 响应）

    // Step 2 数据
    queryText: '',                     // AI 查询原文
    queryResults: [],                  // 查询结果日期列表
    selectedDatesFromQuery: [],        // 从查询结果选中的日期
    selectedDatesManual: [],           // 手动添加的日期
    allSelectedDates: [],              // 合并后的全部选中日期（含补全信息）
    priceSpreadInfo: [],                // 时段价差信息 [{ period, spread_direction, low_probability }]

    // Step 3 数据
    strategyData: [],                  // 策略数据（14列）
    adjustedRatios: {},                // 用户调整比例 { HH:mm: '±X%' }
    actualDeclaredQuantities: {},      // 用户调整电量 { HH:mm: number }

    // 流程状态
    currentStep: 1,                    // 当前步骤
    step1Completed: false,
    step2Completed: false,
    step3Completed: false,

    // Actions
    setDeclarationDate(date),
    fetchDateInfo(date),
    fetchPriceComparison(dates),
    fetchStrategyData(payload),
    submitDeclaration(),
    resetStep(step),
    ...
}
```

### 4.3 数据流向图（从设计稿）

```
manual-date API
    │
    ▼
Step 1: declarationDate → dateInfo + WeatherInfo + PriceChart + UnifiedDispatchChart
    │
    │   declaration_date 传给 Step 2 /
    │   declaration_date 传给 Step 3
    ▼
Step 2: selectedDates（历史日期列表）
    │   └─ 每个日期通过 manual-date API 补全信息
    │
    ▼ (点击「下一步」进入 Step 3 时，链式调用)
① price-comparison-table API ← selectedDates（获取电价对比数据）
    │
    │   成功后直接整理响应数据，提取 price_spread_information（价差方向 + 概率）
    │
    ▼
② strategy-data API ← declaration_date + price_spread_information（获取策略表数据）
    │
    ▼ (①② 均成功后，进入 Step 3 渲染页面)
Step 3: PriceComparisonTable（多日期电价横向对比）
    │   + StrategyTableV2（16列策略表）
    │
    ▼
submit API ← 完整申报数据
```

|------|------|

### 6.2 交互逻辑

| 交互 | 行为 |
|------|------|
| 输入查询 | 用户输入自然语言查询条件，点击「发送查询」 |
| 发送查询 | 调用 `POST /api/query` 发送 `{ prompt: 用户输入 }`，后端由 DeepSeek 大模型生成 SQL 并执行查询，返回结构化日期列表 |
| 选中/取消选中 | 点击行末操作按钮，在「查询结果」和「已选中日期」之间移动。选中行显示蓝色背景 |
| 全选/取消全选 | 批量选中或取消选中查询结果中的所有行 |
| 手动新增日期 | 在「已选中日期」区域顶部选择日期 → 确认添加 → 调用 `manual-date` 补全该日信息 |
| 移除单个 | 点击「✕ 移除」从已选中列表中移除该行 |
| 移除全部 | 清空「已选中日期」列表 |
| 上一步 | 弹出警告确认框："退回上一步将清空 Step 2 所有数据（AI 查询结果 + 已选中日期）" |
| 下一步 | **链式调用两个接口：** ① 先调用 `price-comparison-table` 获取电价对比数据 → ② 成功后**直接整理响应数据**提取 `price_spread_information`，紧接着调用 `strategy-data` 获取策略表数据 → ③ 两个接口都成功后，进入 Step 3 渲染页面 |

### 6.3 AI 查询接口对接

后端已提供 AI 自然语言查询接口，基于 DeepSeek 大模型实现：

| 项目 | 内容 |
|------|------|
| **端点** | `POST /api/query`（路由文件 `routes/aiQuery.js`，挂载于 `app.use('/api', aiQueryRouter)`） |
| **请求** | `{ prompt: "查找前7个星期三且是雨天且温度在23至26度之间的日期" }` |
| **成功响应** | `{ status: 0, msg: 'SUCCESS', data: [...] }` |
| **失败响应** | `{ status: 1, msg: '错误描述', data: [] }` |
| **接口逻辑** | 接收自然语言 prompt → DeepSeek 生成 SQL → 安全校验 → 执行 MySQL 查询 → 返回结构化数据 |
| **返回字段** | `date`, `date_type`, `day_of_the_week`, `holiday_name`, `temperatureMin`, `temperatureMax`, `cloudCoverEarlyMorning`, `cloudCoverMorning`, `cloudCoverAfternoon`, `cloudCoverEvening`, `windSpeed`, `windDirection`, `weather` |

> 注意：在 `@/utils/request.js` 中已配置 axios 拦截器，`POST /api/query` 会通过 proxy 自动转发到后端。前端在 `api.js` 中封装调用函数即可，无需额外处理跨域或 baseURL。

### 6.4 API 对接

| 接口 | 触发时机 | 请求参数 | 响应映射 |
|------|----------|----------|----------|
| `POST /api/query` | 用户点击「发送查询」时 | `{ prompt: 用户输入 }` | `data[]` → `QueryResultTable` 渲染 |
| `POST /manual-date` | 手动新增日期确认时 | `{ date }` | 返回该日期的日期信息/天气/温度等 |
| `POST /price-comparison-table` | 点击「下一步」进入 Step 3 时 | `{ dates: selectedDates }` | 返回各时段各日期的电价/价差/价差方向/概率 |

### 7.2 策略申报表 16 列明细

| 列 | 字段 | 数据来源 | 说明 |
|----|------|----------|------|
| 1 | 时段（时间） | — | 固定列（左固定），`00:00`~`23:00` |
| 2 | 多日合约电量 | `strategy-data` API | 第三方数据 |
| 3 | 周合约电量 | `strategy-data` API | 第三方数据 |
| 4 | 月度合约电量 | `strategy-data` API | 第三方数据 |
| 5 | 年度合约电量 | `strategy-data` API | 第三方数据 |
| 6 | 中长期合约电量 | 自动求和（2+3+4+5） | 公式计算 |
| 7 | 用户评估电量(MWh) | `strategy-data` API | 第三方数据 |
| 8 | 价差方向 | Step 2 导入（`price-spread-info`） | 展示「日前高」/「日前低」 |
| 9 | 日前低概率 | Step 2 导入（`price-spread-info`） | 展示百分比 |
| 10 | 方案一 | `strategy-data` API（`plan_a`） | = max(中长期, 用户评估) |
| 11 | 建议调整比例 | `strategy-data` API | 查表所得 |
| 12 | 方案二 | `strategy-data` API（`plan_b`） | = 方案一 × (1 + 比例) |
| 13 | 日前申报电量 | `strategy-data` API（`declared_quantity`） | clamp 后结果 |
| 14 | 申报比例 | 自动计算 | = 申报电量 ÷ 评估电量 |
| **15** | **调整申报比例** | **用户编辑** | **可编辑列（黄色背景）**，设计稿中是 `✎` 编辑图标 |
| **16** | **实际申报电量(MWh)** | **用户编辑后联动** | **根据调整申报比例变化** |

### 7.3 核心交互逻辑

**价差方向 & 日前低概率的计算规则**（来自设计稿注释）：

- 对每个时段，统计 N 个选中日期中「日前 < 实时」的次数
- **价差方向**：如果超过半数日期为「日前 < 实时」，则方向为「日前低」，反之为「日前高」
- **日前低概率**：日前 < 实时的日期数 ÷ 总日期数（如 3/4 = 75%）

**策略表编辑逻辑：**

- **第 15 列「调整申报比例」**：用户可点击 `✎` 图标编辑数值，默认值为接口返回的 `declared_ratio`
- **第 16 列「实际申报电量」**：根据用户修改的「调整申报比例」自动重算 → `declared_quantity × (新比例 / declared_ratio)`
- 编辑后的值在 `store` 中独立存储（`adjustedRatios` 和 `actualDeclaredQuantities`），用于最终的 submit 请求

## 附录 A：关键设计决策

### A.1 为什么用 Pinia Store 而非组件内状态？

三步流程之间需要共享大量数据（如 Step 2 的价差信息流向 Step 3），如果使用组件内状态或 provide/inject，跨步骤数据传递会非常复杂。Pinia 提供了集中式的状态管理，且支持 Vue DevTools 调试。

### A.2 为什么新建路由而非复用 v1 路由？

v1 和 v2 的路由守卫、权限控制、面包屑层级各不相同。独立路由避免了与 v1 的冲突，也方便将来独立部署或灰度发布。

### A.3 步骤间数据持久化

用户在 Step 2 点击「上一步」时，设计稿要求清空 Step 2 数据。但用户如果只是点击步骤 1 查看（而不点退回确认），应该可以无损返回。因此「上一步」按钮触发的弹窗确认是关键交互节点。

### A.4 StrategyTableV2 与 v1 StrategyTable 的关系

v2 的策略表有 16 列（v1 为 14 列），列结构完全不同，且有双表头、固定列等增强功能。因此不直接复用 v1 的 `StrategyTable.vue`，而是新建 `StrategyTableV2.vue`，但在 UI 风格（配色、字体、间距）上保持与 v1 一致。
